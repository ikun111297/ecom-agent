# 电商智能客服 Agent

基于大模型（DeepSeek）的电商售前导购 + 售后自动化客服系统，支持 RAG 知识库检索与订单工具调用。

## 功能

- **售前导购**：根据用户需求推荐商品、回答参数、引导下单
- **售后自动化**：查询订单状态与物流、退换货规则问答
- **RAG 检索增强**：知识库切块 + 查询改写 + BM25 检索 + 实体命中闸门 + 相对分数过滤
- **工具调用**：模型自主调用 `query_order` 查询订单，并按订单归属校验权限
- **多渠道**：命令行 / 飞书机器人，业务逻辑与渠道完全解耦
- **自动评测**：LLM-as-judge，售前 / 售后分开统计

## 架构

```
knowledge/  data/                       数据层：知识库文档、订单数据
      |
core/
  knowledge.py    知识库加载与清洗
  retriever.py    切块 + 查询改写 + BM25 检索 + 两道相关性闸门
  tools.py        订单查询工具（含归属校验）
  llm.py          大模型调用封装（模型/温度/地址可配置）
  prompts.py      售前 / 售后 提示词
  sales.py        售前逻辑
  aftersales.py   售后逻辑（含工具调用循环）
      |
channels/
  cli.py          命令行渠道
  feishu.py       飞书机器人渠道（长连接 + 线程池）
```

新增渠道只需实现 `new_history()` 与 `ask(question, history, user_id)` 两个接口，`core/` 无需改动。

## 技术要点

### RAG 流程

1. 知识库按空行切块，每块一个独立知识点
2. 用大模型把口语问题改写成检索关键词（解决"多少钱"匹配不上"价格"的词汇鸿沟）
3. BM25 打分，改写词与原词共同参与打分，改写跑偏时原词兜底
4. 用户明确提到的商品，对它的**商品详情块做乘法加权**（不是给所有含该商品名的块加常数 —— 加常数会把强弱命中的差距压平）
5. 两道闸门决定要不要把资料喂给模型：
   - **闸门 1（实体命中）**：问题里必须出现至少一个知识库实体（商品名，或知识块首行里的实词）。一个都没命中，直接返回"未检索到"，不给模型任何资料。
   - **闸门 2（相对分数）**：只保留分数 ≥ top1 × 0.5 的块，避免弱相关块稀释上下文。

**为什么不用固定分数阈值**：BM25 分数没有归一化，绝对值随语料规模漂移。实测在本项目语料里，单个词命中一次就能拿 1.9~2.7 分，而 BM25 对负 IDF 词的兜底值（`epsilon × average_idf`）是 0.46 —— 和"0.5 阈值"处在同一量级，所以固定阈值区分不了"相关"与"不相关"。更麻烦的是，像「你们的眼霜能用吗」这种主体商品不在知识库、但句式用词（"能用""吗"）在语料里的问题，会轻松击穿阈值，把『敏感肌能用吗』『运费谁承担？』等完全无关的资料塞进上下文。

### 防幻觉设计（三层）

| 层级 | 手段 |
| --- | --- |
| 检索层 | 实体命中闸门 + 相对分数过滤，无实命中时不提供任何资料 |
| 工具层 | 订单数据只能由 `query_order` 提供；按 `user_id` 校验订单归属；返回前剔除客户姓名 |
| 提示词层 | 禁止"我帮您确认一下""稍等片刻"等无法兑现的话术；要求订单信息只能引用工具返回结果 |

### 安全

- **订单归属校验**：`user_id` 由渠道层注入并强制覆盖模型传参，模型无法伪造身份。没有这道校验时，任何人输入别人的订单号就能拿到别人的订单明细。
- **不把客户姓名交给模型**：`query_order` 返回结果里剔除了姓名等个人信息，模型即使想复述也没有数据。

### 分层架构

渠道层只负责收发消息，业务逻辑集中在 `core/`。飞书渠道把回复放进线程池异步执行，避免一个用户的提问阻塞其他用户；同一用户的消息串行处理，保证会话历史不被并发改写。

## 评测结果

22 条用例，售前 / 售后分组，反向用例交给裁判模型判断"是否诚实"，并额外检查检索层有没有真的拦住：

| 指标 | 结果 |
| --- | --- |
| 售前准确率 | 11/11 |
| 售后准确率（含订单查询、越权拦截） | 6/6 |
| 反向诚实率（知识库里没有的商品） | 4/4 |
| 边界诚实率 | 1/1 |
| 检索层拦截率 | 4/5 |

评测采用 LLM-as-judge：由模型判断回答是否准确表达期望语义，避免关键词匹配的脆弱性（实测中模型答"可以用"而词表写"可用"会误判）。

> 注意：这 22 条用例的作用是**回归测试**（确认改动没让已有行为回退），不是效果证明。用例的期望要点直接来自知识库，规模也偏小。真正有价值的信息在失败案例里，建议跑出结果后逐条看。

## 快速开始

```bash
pip install -r requirements.txt
cp .env.example .env   # 然后填入 DEEPSEEK_API_KEY
```

运行命令行版本：

```bash
python -m channels.cli
```

运行飞书机器人：

```bash
python -m channels.feishu
```

运行评测：

```bash
python -m eval.run_eval
```

## 配置

全部通过环境变量（见 `.env.example`）：

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `DEEPSEEK_API_KEY` | 无 | 必填 |
| `DEEPSEEK_MODEL` | `deepseek-chat` | 换模型不用改代码 |
| `DEEPSEEK_BASE_URL` | `https://api.deepseek.com` | 接口地址 |
| `LLM_TEMPERATURE` | `0.3` | 业务回答温度（检索改写和评测裁判固定用 0） |
| `FEISHU_APP_ID` / `FEISHU_APP_SECRET` | 无 | 用飞书渠道时必填 |
| `DEMO_USER_ID` | `U1001` | 命令行渠道的演示身份（订单归属校验用） |

## 知识库格式

`knowledge/` 下的 Markdown 文件会被自动加载，新增或替换文件**无需修改代码**（改了文件内容会自动重建索引）。

商品：

```markdown
## 商品名称

- 价格：99元
- 卖点：补水保湿、敏感肌可用
- 规格：25ml × 10片
- 库存：有货
```

问答（FAQ / 售后规则通用）：

```markdown
Q：敏感肌能用吗？
A：XX面膜敏感肌可用，建议先耳后测试。
```

## 已知限制

- **检索闸门靠实体表命中**。像「防晒霜孕妇能用吗」这种"主体商品不在知识库、但问句里的次要词（孕妇）在库"的问题会通过闸门，目前靠提示词层兜住（实测回答是诚实的，但检索层并不干净）。要根治需要识别"句子主体"，可以引入 embedding 检索或更细的意图分类。
- **多轮指代检索不到**：「那它的价格呢」这类追问，因为每轮只用当前问题做检索，拿不到上一轮的实体。
- **飞书去重表存在内存里**，进程重启后失效；生产环境建议换成 Redis 之类的持久化去重。
- **`resolve_user_id()` 目前是演示实现**（所有飞书用户映射到同一个业务用户）。接真实账号体系时替换这个函数即可。
- 单条知识块长度不足 20 字符会被静默丢弃（`split_chunks` 里的过滤），新增短 FAQ 时留意。
